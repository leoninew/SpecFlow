# Intent / 意图：工作量评估、DAG 拆分与多会话协作
最后修改时间: 2026-10-10 21:29:19

## Review status / 审查状态

Accepted

## Workflow / 流程

Intent / 意图 → Plan / 计划 → Implementation / 实现 → Verification / 验证

用户要求汇总讨论并开始 Plan / 计划，按阶段约定接受本意图，随后明确统一流程。任务复杂度只决定是否增加 task / 子任务文档；所有任务采用相同阶段。文档格式、脚本配套、实施拆分与当前执行情况见同名总计划。

## Background / 背景

实际使用中，一个较粗的任务可能在模型分析和实现过程中不断扩展，最终产生大量工作和变更，增加用户理解、纠正、review 和集成的成本。

现有协议要求目标、边界和验收，但没有明确的工作量评估、子任务拆分、依赖放行及跨会话交接要求。用户希望在同一个主会话内梳理整体任务，以 DAG 表达依赖，再按用户要求交给其他可见会话或子 agent，主会话协调和审查结果。

用户重视随时查看执行进展、直接与执行者交流和纠正，因此默认采用用户复制提示词到独立可见会话的方式。SpecFlow 继续作为开发协议，不承担会话运行时。

## Goals / 目标

- 统一为意图、计划、实现、验证四阶段，消除流程模式选择；任务复杂度只决定是否增加子任务文档。
- 模型结合仓库事实评估工作量、复杂度、风险和未知项，说明拆分或保持单任务的依据。
- 以可独立说明、交付、检查和审查的结果作为子任务边界，限制单次变更与 review 的复杂度。
- 根据任务大小使用适量文档；大任务共享总意图、总计划，按节点建立子任务文档。
- 总意图分析拆分与依赖；总计划统一维护可执行 DAG、任务表及分配记录。
- 前置实现满足约定条件后，后续任务才能被分配；共享文件与契约冲突另行判断。
- 主会话承担协调与仲裁角色，在用户要求后登记任务分配并输出绑定具体任务的提示词。
- 执行会话能够直接与用户交流，依据文档接收、实施和交付；主会话读取交付记录并 review。
- 发现规模膨胀、依赖变化或范围偏离时，修订相关任务并分析影响。
- 修改本项目的 skill、模板和必要的 CLI / 脚本配套，使协议能通过现有安装与发行方式交付。

## Non-goals / 非目标

- 不以固定工时、文件数或代码行数作为所有项目的拆分硬阈值。
- 不要求小任务创建独立子任务文档，也不要求每个子任务重复建立完整阶段文档。
- 不要求 Intent 提前完成所有技术设计，初始拆分允许在计划和实施中有记录地细化。
- 首版不实现任意 Agent 自由抢任务所需的原子认领、分布式锁或集中调度服务。
- 不自动创建会话、调用子 agent、发送外部消息、合并分支或修改用户级插件安装状态。
- 不把安装同步脚本改造成任务调度器，不把 CLI 改造成主要流程驱动入口。

## Workload assessment / 工作量与粒度

评估至少覆盖：交付目标是否可分离、职责边界与修改影响、关键未知项、验证范围、review 所需上下文，以及拆分后的耦合和共享修改。

每个子任务应有一个主要交付结果、明确的范围和可检查的验收要求。多个独立结果通常应拆开；影响任务边界的方案未定时，可先安排调查或设计任务，交付可供后续使用的结论。这些判断用于决定是否建立 task，不改变阶段和基本文档种类。

工作量、复杂度和风险分别说明。高风险的小改动可能需要更深入的设计和验证，不应只为了增加节点而拆分。文件数、行数和预计 review 时间可作提醒信号，需要根据实际使用校准。

对子任务重复评估：仍然过粗时继续拆分；无法单独说明输入输出或拆分造成过度协调时调整边界。实施中发现新目标或更大范围时，执行者报告并由主会话重新安排。

## Document structure / 文档结构与流程归属

- 所有任务采用 Intent → Plan → Implementation → Verification，阶段记录为 Intent、Plan、Verification；Implementation 是实际开发，不额外要求一份实现文档。
- 小任务保留意图、计划和验证文档，内容按实际范围简明填写，无需独立 task；跨会话交接可以直接引用这些文档。
- 大任务共享一个总意图、一个总计划和一份总验证记录，按节点增加 task 文档。
- 技术设计写入总计划或相关 task；Spec 不再是独立阶段，不依据复杂度再生成额外规格或多套阶段文档。
- 意图阶段说明拆分依据、任务边界、输入输出和初始依赖；进入计划后，总计划成为可执行任务与依赖的权威来源。
- 子任务文档承载局部实施安排、接收与进展、检查证据、交付和 review 记录，不要求各节点重新启动一套父级流程。
- 子任务的开发检查和交付审查用于放行依赖；整体 Verification 检查集成结果、总体验收和范围一致性。
- 阶段文档的 Review status 继续使用 Draft / Accepted；任务执行情况和交付审查另行记录，文档 Accepted 不表示代码已经交付。
- 用户接受总计划后，其覆盖的子任务方案随之接受；执行授权仍以用户明确要求的阶段和范围为准。

## Dependencies and eligibility / DAG 与可分配条件

A → B 表示 B 依赖 A 的交付结果。每条直接依赖说明所需结果和理由；标识唯一、引用有效、无自依赖、无环，且总体验收项有明确归属。

默认只有前置任务同时满足以下条件，后续任务才可分配：

1. 已提交约定的实现或调查 / 设计产物。
2. 约定的必要检查已通过，或明确说明该交付为何不适用。
3. 主会话已 review 并接受交付。
4. 交付版本明确，后续执行者能在其工作基线上访问和使用。

任务自身还需满足：方案与执行阶段获授权、尚未分配、没有未解决的阻塞或执行冲突。可分配结论依据这些事实推导，派发前重新检查；表格可展示结论和原因，但不是无条件的执行许可。

没有交付依赖不等于可以同时修改共享文件或契约。总计划需写明隔离、串行或协调安排，并明确最终集成责任。

## Coordination and handoff / 仲裁、分配与交接

一个主会话负责维护权威总计划、任务归属和全局依赖。默认交给用户可见的独立执行会话；用户明确要求时，子 agent 可使用相同文档和分配约定。

用户要求派发后，主会话检查可分配条件，登记执行者代号和唯一分配编号，再输出提示词。登记表示责任已安排；执行者接收后才记录开工事实。

提示词携带：权威文档位置、任务 ID、分配编号、工作基线、授权阶段、目标与范围、前置交付要求、检查与交付要求。执行者核对分配有效性后开展工作，不通过自行改写总计划取得任务归属。

执行者将接收、进展、阻塞和交付记录写入约定位置。用户可以直接在执行会话里讨论实现；任务边界、依赖或共享契约变化由主会话协调并更新权威记录。

重新分配前核实原执行者情况、通知停止或协调剩余工作，撤销旧编号并保留历史；超时不能自动视为已停止。旧编号的交付需要主会话重新核对，不能直接作为当前任务已接受的证据。

跨 worktree 时要明确共享的权威协调记录位置，代码可在独立工作区实施。不同分支中的计划副本不能独立授予执行权。文档协议依赖单一写入者和参与者遵守约定，不宣称具有原子互斥能力。

## User stories / scenarios / 用户故事 / 场景

1. 小任务说明规模判断，在已有阶段文档内完成，无额外认领文档负担。
2. 大任务由一个主会话完成拆分和计划，用户选择已满足条件的节点，取得交接提示词。
3. 用户将提示词粘贴到新会话，直接查看、交流和纠正执行；主会话按文档 review 交付。
4. 多个执行者请求同一任务，由主会话顺序登记，任务仅有一个有效分配编号。
5. 上游已提交但尚未被接受时，下游等待；上游被接受且交付可用后，才允许分配。
6. 并行任务需要修改同一范围时，主会话先安排隔离或串行。
7. 实施中发现工作量膨胀或上游变化时，主会话修订拆分、评估下游影响并重新派发。
8. 子任务分别交付后，整体还需验证集成和总目标。

## Acceptance criteria / 验收标准

- A01：Intent 规则及模板要求有依据的工作量评估，包含拆分、保持单任务和调查前置任务的判断。
- A02：所有任务使用统一四阶段与意图、计划、验证记录，移除模式选择及独立 Spec 阶段；复杂度只决定是否建立可独立交接的 task 文档。
- A03：统一计划记录有效 DAG、依赖交付条件、任务范围和验收归属，并能检查缺失、循环和遗漏。
- A04：派发前检查前置实现、必要检查、仲裁接受、交付可用性和工作区冲突。
- A05：总计划单一仲裁写入，记录执行者、有效分配编号和重新分配历史，明确文档协议的并发边界。
- A06：默认可见会话交接，提示词仅按用户要求生成，携带任务、基线和阶段授权；生成提示词不自动启动执行者。
- A07：执行者可以回报接收、进展、阻塞和交付，用户能直接交流，主会话能通过约定记录 review。
- A08：范围扩大、依赖变化、撤销与重新分配有明确处理约定。
- A09：子任务交付审查与整体 Verification 各有职责，集成及全部验收项有负责人。
- A10：CLI 初始化意图、计划、验证及辅助模板，正确识别规范审查标题；task / handoff 不成为阶段，Spec 不再作为新流程的活动阶段；保留三种既有文档布局，不主动删除历史资料。
- A11：源码、发行包和原生插件交付能够提供新增资源，skill、模板和中英文说明一致。
- A12：通过小任务、串行依赖、并行冲突、竞争分配、跨会话交接、重新拆分及集成场景核对行为，并执行项目既有检查。

## Open questions / 待定问题

总体目标和协作方向已明确，无必须阻止进入 Plan 的未决事项。

子任务目录、表格字段、脚本支持边界、发行资源实现和具体检查方式已在同名总计划及其子任务方案中明确；用户要求开始 T01 后，方案标记为 Accepted，执行授权仍以总计划登记为准。未来原子认领工具和发布版本不在本轮自动决定。

## Decisions / 决策

- 采用唯一流程 Intent → Plan → Implementation → Verification，移除 strict、standard、light 的模式选择；standard 不再作为需要用户认识的模式名称。
- 小任务与大任务都保留意图、计划和验证，复杂度只决定是否增加 task 文档。
- 共享总意图，每个子任务一份 task，技术设计和局部实施安排在计划或 task 内表达。
- Spec 退出独立阶段，历史模式与规格文档作为历史资料保留，不批量改写或删除。
- 以总计划作为可执行依赖和分配登记的权威来源，总意图保留拆分分析。
- 前置交付被主会话接受且可供下游使用后，才放行后续任务。
- 主会话承担仲裁角色，按用户要求分配任务并输出交接提示词。
- 默认通过用户可见的独立会话执行，子 agent 保留为用户选择的方式。
- 首版以文档协议和必要脚本配套实现目标，不引入自由抢任务或调度服务。

## Risks / assumptions / 风险 / 假设

- 工作量判断可能低估，必须允许基于新证据修订，不能保证一次拆分准确。
- 文档协议不能阻止不遵守约定的重复执行，也不能解决不同机器上的原子认领。
- 用户把同一份分配提示词交给多个会话时，需要主会话核实和重新分配。
- 代码基线、权威计划和任务交付位置若不一致，可能造成过时执行或重复集成。
- 过细拆分和重复文档会提高协调成本，必须保留小任务路径。
- 上游变更可能使已接受的下游结果失效，需保留交付版本并分析影响。
- 首版脚本不能仅凭状态文字证明实现正确，语义验收仍由主会话负责。
