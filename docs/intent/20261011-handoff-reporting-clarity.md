# Intent / 意图：明确跨会话接收、回报与状态更新
最后修改时间: 2026-10-11 09:25:41

## Review status / 审查状态

Accepted

## Background and goals / 背景与目标

0.2.0 已规定总计划仲裁、task 回报及交接提示词，但接收与完成时的必做动作、状态更新责任和通知方式分散在段落中。用户明确要求更新 skill 和文档消除歧义。

让独立执行会话从交接信息中明确授权依据、允许修改的记录位置、开工与交付步骤；让主会话依据回报同步总登记，避免执行者只在聊天中说完成，或把方案 Accepted 当成执行完成。

## Workload assessment / 工作量评估

保持单任务：交付结果是同一套交接责任约定，修改集中在 skill、协作参考、三份模板和双语 README。无代码或发行机制变化，适合一次文档审查；拆分会增加相同规则的同步成本。技术复杂度低，主要风险是措辞互相冲突或增加重复状态。

## Acceptance criteria / 验收标准

- A01：派发材料明确协议入口、权威计划、有效分配、授权来源与范围、基线及可写回报位置；任务路径本身不自动授予执行权。
- A02：执行者开工前记录接收，关键进展或阻塞时更新记录，交付前完整写入变更、验收结果、检查、版本、未完成项与风险。
- A03：总登记状态仅由主会话维护，明确 assigned → running → submitted → accepted / running 的证据与时点；task 方案状态不作执行进度。
- A04：明确默认由用户转交回报摘要；无自动跨会话通知承诺；记录不可访问、写入失败、编号失效及总登记滞后的处理明确。
- A05：skill、模板、契约与双语使用说明一致；无 task 时复用既有记录，不增加任务文档或第二套执行状态。

## Non-goals and risks / 非目标与风险

不增加 CLI 状态自动化、自由认领、原子锁、自动消息发送或新状态；不刷新用户级插件、不发布或提交。文档检查不证明真实多会话必然遵守协议；用户已有模板不会被 init 覆盖。

## Decisions and review / 决策与审查

用户在确认现有责任分工后要求直接完善，按已有授权补齐意图和计划并实施。保留“执行者写 task，主会话维护权威状态”的设计，只明确操作时点和证据。暂无需要用户确认的未决事项。
