# Intent / 意图术语迁移
最后修改时间: 2026-09-12 14:20:11


## Review status / 审查状态

Accepted

## Mode / 模式

strict / 严格

## Background / 背景

当前协议将软件变更的起点称为 Intent / 意图，并在文档路径、CLI 输出、模板、README、技能说明和历史过程文档中使用“意图”或“意图”相关表述。需要统一迁移为 Intent / 意图，使概念和对外文字保持一致。

## Goals / 目标

- 将项目内面向用户和维护者的 Intent / 意图、intent / 意图等表示软件变更起点或工作项的术语统一为 Intent / 意图。
- 将协议的第一阶段、阶段目录、模板、CLI 状态输出、README（中英文）、插件技能、测试和过程文档同步为新术语。
- 使新安装的插件和新初始化的项目只产生 Intent / 意图术语及 `docs/intent/` 布局。
- 更新现有项目内的历史过程文档与引用，确保仓库中不再遗留该语义下的旧术语。

## Non-goals / 非目标

- 不改变 strict、standard、light 三种流程模式及其其余阶段的业务含义。
- 不扩大为对与软件变更无关的自然语言进行机械替换。
- 不维护旧目录或旧术语的兼容接口。

## User stories / scenarios / 用户故事 / 场景

- 作为使用者，我可以用 Intent / 意图描述并启动一个软件变更，而不需要接触 Intent / 意图或 intent / 意图术语。
- 作为维护者，我运行 `specflow init` 后，得到的模板和目录采用 Intent / 意图命名；运行 `specflow status` 时，看到的阶段名称也采用该命名。
- 作为仓库读者，我在文档和示例中只能看到一致的 Intent / 意图概念。

## Acceptance criteria / 验收标准

- 项目源代码、测试、插件清单、技能、模板、README、CI 说明和过程文档中，不再将旧术语用于表示软件变更起点或工作项。
- 第一阶段的规范名称为 Intent / 意图，文档目录为 `docs/intent/`，CLI 输出和初始化行为与其一致。
- `specflow status` 能正确发现并报告采用新布局的过程文档。
- 自动化检查、单元测试和打包流程通过。
- README 明确这是不兼容的术语与目录迁移，并说明现有项目需要完成迁移。

## Open questions / 待定问题

暂无需要用户确认的未决事项。

## Decisions / 决策

- 采用 strict / 严格模式，因为这会改变公开术语、目录契约和 CLI 观察结果。
- 本项目只使用 Intent / 意图的新术语和语义，不保留旧目录的扫描、生成或输出行为。
- 仓库内的历史过程文档、路径、文件名和引用一并迁移，不保留旧术语作为历史事实。
- 替换范围覆盖表达软件变更起点或工作项的所有中英文术语、代码标识符和用户可见文本；与该语义无关的普通用语逐处审查后保留。
- 新过程记录本身以 Intent / 意图为标题；实施时会随目录契约一并移动。

## Risks / assumptions / 风险 / 假设

- 将旧目录改为 `docs/intent/` 是有意的破坏性变更；外部已有项目必须迁移后才能被新版本识别。
- “所有”若按纯文本进行替换，可能误伤与协议无关的描述；实现必须基于语义逐处审查。

## User review notes / 用户审查记录

- 用户确认所有相关概念均使用新术语和语义；不保留旧名称兼容，并迁移历史文档。
- 用户澄清不改变整体文档布局；只将第一阶段目录及其中的全部文件从 `docs/intent/` 迁移到 `docs/intent/`。
