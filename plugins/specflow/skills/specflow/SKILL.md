# SpecFlow

SpecFlow 定义开发阶段、文档和交付审查，coding agent 负责实际开发，用户决定如何安排执行会话。讨论和过程文档以中文为主，命令、路径与代码标识符保留原文。

## 流程与授权 / Workflow and authorization

所有任务采用 Intent → Plan → Implementation → Verification。复杂度只决定是否增加 task，小任务也有计划。

阶段文档及 task 方案使用 `Draft` / 草稿、`Accepted` / 已接受；历史 `Approved` 按已接受理解。方案状态与任务执行状态分开，方案 Accepted 不表示实现已完成。

- 聚焦用户授权的阶段和范围。满足阶段完成条件，且用户接受或已授权推进时，接受前置文档并继续；有效授权与已确认决策可以沿用。
- 只要求开始 Intent 时，交付意图供审查。已要求实现但前置记录缺失时，先完成意图和计划；连续执行授权不能代替澄清和策划。
- 接受总计划时一并接受其覆盖的 task 方案；具体节点仍按授权与依赖执行。
- Implementation 包含必要开发检查和子任务审查。默认汇报实现结果后等待整体 Verification 的授权；已授权连续实现和验证时，先输出实现摘要与验证前风险，再切换阶段。
- 交接提示词引用已有授权，不自动启动会话或子 agent，也不额外授权 Git 写入或发布。

## 文档与模板 / Documents and templates

同一功能使用相同的 `<yyyymmdd>-<feature>` 标识，例如 `20260609-report-export`。按阶段读取模板：

| 文档 | 项目内路径 | 模板 |
| --- | --- | --- |
| 意图 | `docs/intent/<yyyymmdd>-<feature>.md` | [intent.md](template/intent.md) |
| 计划 | `docs/plan/<yyyymmdd>-<feature>.md` | [plan.md](template/plan.md) |
| 验证 | `docs/verification/<yyyymmdd>-<feature>.md` | [verification.md](template/verification.md) |
| 拆分后的子任务 | `docs/task/<yyyymmdd>-<feature>/<task-id>-<topic>.md` | [task.md](template/task.md) |
| 用户要求的交接提示词 | 不作为独立阶段文档 | [handoff.md](template/handoff.md) |

小任务保留意图、计划和验证记录；拆分时共享父级记录，每个节点增加一份 task，承载局部方案、进展和交付。Implementation 不另建阶段文档，task 不重复父级流程。

过程文档的大标题下一行保留 `最后修改时间: <yyyy-MM-dd HH:mm:ss>`，修改时写当前时间。已有定制模板可以沿用，内容须符合当前契约；篇幅按实际范围调整。

“新的意图”“开始意图”或“新 feature”默认新建；“更新现有意图”“继续上次”或明确指定文档时沿用。上下文无法判断时再澄清。历史 `docs/spec`、旧模板及模式字段保留，不参与新流程。

## Intent / 意图阶段

1. 查明背景、目标、范围、场景、约束与验收。核对仓库事实和已有答复；仍不明确的事项在本阶段向用户提问，将答复和决策写入意图。
2. 评估交付结果、职责影响、技术未知项、检查与审查范围及协调成本，给出工作量、复杂度、风险和是否拆分的依据。每个候选 task 应有一个主要结果、明确输入输出和可检查验收；文件数、行数和时间仅作参考。
3. 按意图模板整理结论；拆分时列出候选节点、初始依赖与验收归属，不登记分配。

完成条件：目标、边界和验收一致，意图疑问已沟通解决。尚待答复时保持 Draft，不进入 Plan；假设或风险记录不能代替确认。

## Plan / 计划阶段

1. 完成确定开发方案所需的调查与可行性验证，记录技术选择、接口与数据约束、兼容性及决策依据。常规选择依据仓库惯例处理，需要用户决策时在本阶段沟通。
2. 理清全部实施步骤、修改范围、检查、集成和回滚安排，使每个验收项都有对应开发与检查。拆分时，在本阶段完成所有 task 的局部设计、实施步骤和检查方案；共享决策留在总计划。
3. 拆分时按[协作契约](references/task-coordination.md)建立任务定义、DAG、执行登记和共享修改安排；无 task 时协调节写“不适用”。

完成条件：全部开发事项已确定，计划及 task 可直接用于实施。设计缺口在 Plan 内解决，不能留给实现或后续调查节点；普通局部代码写法无需预先确定。

## 协调与交接 / Coordination and handoff

建立或调整 DAG、分配任务、交接、审查交付及重新安排时，读取[协作契约](references/task-coordination.md)。它定义权威记录、可分配条件和状态更新；模板提供实际填写字段。

主会话维护总计划并仲裁交付，执行者在各自 task 回报事实。用户要求交接时，默认输出供独立可见会话使用的提示词；明确选择子 agent 时使用相同记录。主会话直接实施节点也登记分配与交付。

无 task 时引用已有意图和计划，在计划中约定接收、进展和交付位置，不为交接新增 task 或登记表。

## Implementation / 实现 / 开发阶段

1. 读取已接受的意图、计划及本次 task，核对授权、基线和前置交付，按确定的方案实施。跨会话接收和回报遵循协作契约。
2. 运行与改动相关的必要开发检查，记录实际变更、版本、检查结果、未运行项及风险；有 task 时写入交付记录，无 task 时写入计划。
3. 新出现需求疑问或设计缺口时，暂停受影响部分，分别回到 Intent 或 Plan 补齐。同步范围、依赖和受影响交付，满足完成条件后按有效授权恢复。
4. 交付实现摘要，说明变更、检查、风险、范围偏差及待审查事项。主会话依据实际证据接受交付或安排返工，执行者自报完成不足以放行下游。

## Verification / 验证 / 验收阶段

验证授权包含使实现符合已接受意图、计划和 task 的必要修复，无需另行请求 Implementation 授权；用户明确限定只读审查时遵守该限制。

1. 对照意图、计划、task 与实际 diff 核对整体结果、交付版本及集成。发现实现偏差时，先向用户说明对应依据、实际差异和修复方向。
2. 在本阶段立即修复，并使用项目已有检查入口复验修复项及受影响部分；仍有偏差时继续处理。修复以既定验收为准，只有依据不明确、冲突或确需改变目标与方案时，才回到 Intent 或 Plan 处理。
3. 同步最终 diff、task 交付版本及检查证据，按验证模板记录偏差、实际修复和复验结果。客观阻塞无法解决时，说明原因、未通过或未验证的项目及解除条件。
4. 验证完成并确认交付后，在屏幕输出基于实际 diff 的建议 commit message，默认给出 subject、空行和列表 body。检查结果、风险与未完成项放在交付说明中；不将消息写入验证文档或自动执行 Git 写操作。

完成条件：实现与意图、计划及 task 对齐，相关检查通过，交付证据对应修复后的版本。

## CLI / CLI support

`specflow init` 用于初始化，`specflow status` 用于诊断。直接读写过程文档即可推进工作；CLI 输出不代替阶段、依赖或交付的语义审查。
