# Handoff / 子任务交接提示词：<task-id>

最后修改时间: 2026-10-11 09:53:39

仅在用户要求交接并明确授权范围后，填写以下提示词；有 task 时，仲裁会话还需核对可分配条件并登记有效分配。默认交给用户可见的独立会话；提示词生成只表示已安排责任。无 task 时直接引用意图和计划，不另建任务文档。

输出前补全实际值，核对授权来源可读取、执行者和编号与权威登记一致、回报位置可写。下面的字段是已有授权的快照；不能保留未填写的占位符并要求执行者自行推定授权。无 task 时编号与方案修订等不适用字段明确注明，并指定已有计划中的回报章节。

```text
依据 SpecFlow 的统一流程，在以下授权阶段与范围内完成本次任务。父任务流程为 Intent → Plan → Implementation → Verification。

你是本任务的执行会话。先读取并核对以下实际记录：
- 协议入口：<可读取的 SpecFlow SKILL.md 与协作契约路径>
- 权威协调根：<所有执行会话能读取的位置>
- 总意图：<实际路径>
- 权威总计划：<实际路径；不使用其他分支的副本授予执行权>
- 子任务文档：<实际路径；无 task 时引用总意图和总计划>
- 任务 ID：<T01；无 task 时使用父任务标识>
- 执行者代号：<本次分配的执行者>
- 分配编号：<仲裁会话已登记的唯一编号；无 task 时写不适用>
- 方案修订：<本次分配依据的方案版本>
- 用户授权阶段与范围：<实际授权、指令依据及权威计划中的授权记录位置>
- 代码工作区与基线：<实际位置、版本及必要的已接受交付>
- 前置交付及证据：<版本、所需产物、检查和接受记录>
- 目标与验收：<本次交付及验收 ID>
- 允许修改与共享约束：<范围、非目标、隔离和集成要求>
- 接收、进展和交付记录位置：<可写的实际路径与章节；无 task 时为已有计划的指定章节>
- 主会话读取方式与回报渠道：<共享位置或约定的记录交付方式；默认由用户转交当前会话的可复制摘要>

按顺序执行：
1. 核对方案、授权和前置条件，确认所需交付能用于实际基线，且约定记录位置可读取、可写入；有 task 时还须核对权威登记中的分配编号与执行者仍有效。授权缺失或冲突、编号失效或位置不可用时，在当前会话说明具体缺口并暂停受影响的实施；不要自行修改归属或补造授权。已有有效授权沿用，不因换会话重复要求确认；任务路径和方案 Accepted 本身不是授权。
2. 开始产品修改前，先在约定位置写接收时间、执行者、编号、方案修订、授权来源与范围、实际基线和前置版本；无 task 时不适用字段注明原因。更新最后修改时间；输出接收摘要。有效接收成功写入后即可在授权范围内实施，无需等待主会话将总登记从 assigned 同步为 running。写入失败时先回报并解决位置。
3. 在关键进展、阻塞或范围变化时更新文档，写明已做事项、剩余工作和待仲裁事项。用户可直接与你沟通；需要改变边界、依赖或共享契约时回报主会话，暂停超出授权的部分。
4. 宣布交付前，必须先写交付时间、当前编号、实际变更、范围偏差、各验收项结果与证据、可访问版本 / diff 及位置、使用的前置版本、检查命令与结果、未运行项及原因、未完成项、风险及下游影响。无问题时写“无”，更新最后修改时间。记录写入失败时明确说明“交付记录未完成”，提供待补内容，不宣称已登记 submitted。
5. 在当前会话输出下列可复制摘要，默认由用户转交主会话。接收后、需要仲裁时、交付时均须回报；写文档不会自动通知另一会话：
   - 任务 ID / 分配编号：<实际值；无 task 时编号不适用>
   - 本次事实：<已接收 / 阻塞 / 已交付待审查>
   - 记录位置与交付版本：<可访问的路径；接收时交付版本不适用>
   - 检查概况、未完成项与风险：<实际结果或无>
   - 请主会话处理：<同步接收 / 协调阻塞 / 审查交付>

你负责写执行事实；总计划的执行状态由主会话读到记录后维护：接收后同步 running，完整交付后同步 submitted，审查通过才 accepted，返工则回到 running。不要修改 task 顶部 Draft / Accepted 来表示执行进度，也不要自行接受交付。无 task 时记录在已有计划的约定章节，不建立任务登记表，不套用这些执行状态转换。

若只授权 Implementation，完成局部检查和交付后等待后续安排。生成本提示词不额外授权通知其他会话、调用更多执行者、提交、推送或发布。
```
