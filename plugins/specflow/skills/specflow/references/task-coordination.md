# Task Coordination / 子任务协作文档契约

## Flow and document size / 流程与文档规模

所有任务采用 Intent → Plan → Implementation → Verification。阶段记录为意图、计划、验证；实现是实际开发。任务复杂度只决定是否增加 task，技术设计写在计划或 task 中。

小任务保留三类阶段记录，内容可以简明，无需独立任务表与 task。大任务共享父级阶段，建立总计划和每个节点的一份 task；不为每个节点复制整套阶段文档。

工作量判断覆盖交付结果、职责与影响、关键未知项、检查范围、review 上下文，以及拆分后的耦合与共享修改。分别说明工作量、复杂度和风险；高风险的小改动可以加强设计与验证，不必增加节点。

每个节点应有一个主要交付结果、明确范围和可检查的验收。多个可分别交付的结果通常拆开；边界依赖未知方案时，可先形成调查或设计节点。拆分后仍过粗、不能单独说明输入输出或协调成本过高时，调整边界；文件数、行数和时间仅作参考。

## Identity and authority / 标识与权威位置

- 父任务标识采用 <yyyymmdd>-<feature>；阶段文档在 docs/intent、docs/plan、docs/verification 中同名保存。
- 子任务 ID 在父任务内唯一，采用 T 加至少两位数字，例如 T01。跨父任务使用 <feature>/T01 定位，已用 ID 不回收。
- task 路径为 docs/task/<yyyymmdd>-<feature>/<task-id>-<topic>.md。
- 意图阶段记录候选拆分与初始依赖；进入 Plan 后，总计划的定义表是可执行依赖的唯一来源，DAG 与批次是其视图。
- 总计划记录方案修订，边界、依赖或验收变更时递增；执行登记变化不单独改变方案修订。
- 主会话唯一维护分配、当前有效编号、阶段授权、仲裁结论和分配历史。执行者在自己的 task 中回报事实与证据，不自行改写总登记取得任务。
- 跨 worktree 时指定所有会话可访问的权威协调根；任务记录可以共享，代码可以隔离。各分支的计划副本不产生新的执行权。

## Plan fields / 统一计划字段

总计划保留技术选择、实施步骤、修改范围、检查与集成安排。拆分时增加以下信息：

| 协调字段 | 含义 |
| --- | --- |
| 方案修订 | 当前任务定义版本，正整数 |
| 权威协调根 | 权威记录的实际位置 |
| 仲裁会话 | 唯一分配和审查入口 |
| 阶段授权 | 用户已授权的阶段、任务范围与依据 |

任务定义表使用固定列：ID、任务文档、直接前置任务与要求、预期交付与验收、意图验收归属。每条依赖写清所需产物和版本条件；长约束可以引用 task，但依赖边不在两处各自维护。

执行登记表使用固定列：ID、执行状态、执行者、分配编号、工作基线 / 交付位置、仲裁结论 / 当前阻塞。仲裁结论引用实际审查证据；交付版本可以是提交、diff 或可核对的工作区快照，不隐含 Git 写入授权。

分配历史至少保留时间、任务 ID、分配编号、执行者、动作与原因。重新分配后当前登记只指向新编号，旧记录继续保留。

## Review and execution / 审查与执行情况

阶段与 task 方案的 Review status 只用 Draft / Accepted。接受总计划时同步接受其覆盖的 task 方案；这不表示实现完成，也不自动授权所有节点执行。

任务执行登记使用以下状态，全部由仲裁会话依据事实更新：

| 状态 | 所表达的事实 |
| --- | --- |
| unassigned | 尚无有效执行者，是否可分配另行检查 |
| assigned | 已登记执行者与分配编号，尚未收到开工确认 |
| running | 执行者核对后接收，实施或按审查意见返工 |
| submitted | 已回报交付证据，等待仲裁 review |
| accepted | 当前有效交付满足约定条件并被主会话接受 |

执行者报告接收、提交或阻塞，不直接授予自己的交付 accepted。退回返工时保留原有效分配；范围、方案或执行者改变时重新安排并保留历史。阻塞原因另列，不能把 unassigned 当作已经满足条件。

## Eligibility and DAG / 可分配条件与依赖

A → B 表示 B 依赖 A 的交付。核对 ID 唯一、文档存在、引用有效、无自依赖、无环、总体验收有归属，并得到一种合法执行顺序。

派发前逐项重新检查：

1. 总计划与 task 方案已接受，用户授权覆盖本任务当前要执行的阶段。
2. 本任务为 unassigned，没有其他有效分配。
3. 每个直接前置任务已提交约定实现或产物，必要检查通过或有明确的不适用依据。
4. 主会话已接受这些前置交付，版本明确，执行者能够在其基线上使用。
5. 无未解决阻塞，共享文件、契约和工作区冲突已经协调。

可分配是上述事实的结论。手填“可以领取”或执行者自报完成均不能覆盖检查。已分配任务的接收还要核对当前编号、执行者、方案修订与基线。

上游版本改变时，先阻止受影响任务的新派发并通知相关执行者，分析输入与结果是否仍有效。已接受的下游交付需要复核时回到 submitted 并记录原因；需要重新实施时明确授权、安排基线和分配编号，不以旧 accepted 结果放行。

无依赖只说明交付顺序，不证明可以同时写共享代码。计划需明确隔离、串行或协调方式以及集成责任。

## Assignment and handoff / 分配与交接

默认由用户要求将任务交给可见的独立会话。主会话先检查条件，再登记分配，最后按 handoff 模板输出绑定任务的提示词。用户明确选择子 agent 时使用同一套记录，不自动启动执行者。

每次分配生成唯一编号，例如含任务 ID 的 UUID；不能只用“任务尚未完成”判断归属。提示词包含权威位置、任务与执行者、编号、方案版本、阶段授权、工作基线、前置交付、范围和回报要求。

执行者核对有效分配后，在 task 中记录接收、开工、进展和阻塞。用户可以直接沟通实现细节；影响全局边界、依赖或共享契约时回报主会话。主会话按约定记录读取结果，无需转述每条执行消息。

两个执行者同时请求一个任务时，由主会话顺序处理；登记第一个后，后续请求依据最新归属等待或改选任务。此规则依赖单一写入者和参与者遵守约定，Markdown 本身没有原子互斥能力；自由抢任务需要另行实现原子认领。

## Revocation and replanning / 撤销与重新安排

超时不证明执行者停止。撤销前核实执行情况、通知停止并处理尚未结束的共享修改；无法核实时保持阻塞，避免派出冲突执行者。随后记录撤销原因、旧编号和结果位置，安排新基线与新编号。

旧编号的结果作为历史交付保留，由主会话核对后决定是否复用，不能自动更新当前归属或放行下游。任务边界、依赖或验收变更时修订方案，评估受影响的运行任务，并记录继续、暂停或重新分配的决定。

## Delivery and overall verification / 交付与整体验证

每次交付记录当前分配编号、实际范围、可核对版本及位置、使用的前置版本、必要检查与未运行项、风险和对下游的影响。主会话查看实际证据、处理返工，再更新任务登记。

局部开发检查和交付审查用于放行依赖，不自动进入整体 Verification。实现完成后按用户授权进入验证，核对所有当前交付、版本有效性、集成结果、实际 diff 和总体验收；每个节点自称完成不足以证明整体正确。

## Worked cases / 规则走查示例

- 小任务：只有一个明确结果，修改与检查集中。意图说明不拆分依据，计划记录技术选择与步骤，最后形成验证记录；不建立 task。
- 串行依赖：T02 需要 T01 的实现。T01 为 submitted 时等待；成为 accepted 但产物不可访问时仍等待；接受证据和版本均可用后才分配 T02。
- 竞争请求：A、B 同时请求 T01，仲裁者先为 A 登记唯一编号。B 根据最新计划看到 assigned，不能自行覆盖执行者；任意会话绕过仲裁改文件不在协议保证内。
- 重新分配：A 的编号被撤销，B 使用新编号。A 的迟到交付进入历史核对，不能直接把 B 的任务改为 accepted；上游版本变化也须重新检查已交付下游。
