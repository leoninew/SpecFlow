# Task Coordination / 子任务协作契约

[SKILL.md](../SKILL.md) 定义阶段与完成条件；本契约规定拆分后的任务登记、交接和交付审查。

## Records and authority / 记录与权责

- 子任务 ID 在父任务内唯一，采用 T 加至少两位数字，例如 T01，已用 ID 不回收；跨父任务使用 `<feature>/T01` 定位。
- 总计划的任务定义表是依赖的唯一来源，DAG 与批次是其视图。方案修订为正整数，边界、依赖或验收变化时递增，执行状态变化不改变修订。
- 主会话唯一维护分配、当前有效编号、阶段授权、执行状态和审查结论；执行者在自己的 task 中写接收、进展和交付证据。
- 跨 worktree 指定所有会话可访问的权威协调根，明确代码工作区和记录位置；分支计划副本不产生执行权。

## Plan records / 总计划记录

| 协调字段 | 含义 |
| --- | --- |
| 方案修订 | 当前任务定义版本 |
| 权威协调根 | 所有会话可读取的实际记录位置 |
| 仲裁会话 | 唯一分配和审查入口 |
| 阶段授权 | 用户指令依据、阶段及任务范围 |

任务定义表使用固定列：ID、任务文档、直接前置任务与要求、预期交付与验收、意图验收归属。每条依赖写清所需产物和版本条件，长约束可引用 task。上游代码可以尚未交付，但下游使用的接口和约束须在 Plan 内确定。

执行登记表使用固定列：ID、执行状态、执行者、分配编号、工作基线 / 交付位置、仲裁结论 / 当前阻塞。审查结论引用实际证据；交付版本可为提交、diff 或可核对的工作区快照，不隐含 Git 写入授权。

分配历史保留时间、任务 ID、编号、执行者、动作与原因。当前登记只指向有效分配，旧记录继续保留。

## Dependencies and eligibility / 依赖与可分配条件

A → B 表示 B 依赖 A 的交付。计划须核对 ID 唯一、文档与引用有效、无自依赖、无环及总体验收归属，图表表达同一组依赖。无依赖也需安排共享修改的隔离、串行与集成责任。

派发前重新核对：

1. 总计划与全部 task 方案已接受，用户授权覆盖当前任务和阶段。
2. 任务为 unassigned，无其他有效分配。
3. 直接前置已交付约定产物，必要检查通过或明确不适用。
4. 主会话已接受前置交付，版本可用于执行者的实际基线。
5. 阻塞及共享写入冲突已解决。

submitted、自报完成或不可访问的 accepted 产物均不满足放行条件。

## Assignment and reception / 分配与接收

用户要求交接后，主会话核对条件，登记执行者、唯一编号、方案修订、实际基线及授权来源与范围，再填写 handoff。提示词须指定可读协议入口、可写记录位置与主会话读取方式，填写实际值；仅生成提示词不启动执行者。

执行者核对当前编号、执行者、方案、授权、前置版本及记录可读可写性，在产品修改前写入接收记录。缺失、冲突或失效时回报并暂停，不自行补造授权或修改归属；任务路径和方案 Accepted 本身不是授权。有效接收落盘后即可按已有授权实施，无需等待总登记同步 running。

无 task 时交接直接引用父级意图与计划，约定计划中的接收、进展和交付章节及写入范围，沿用记录与回报要求；分配编号和执行登记不适用。

## Reporting and review / 回报与审查

执行者在接收、关键进展、阻塞、范围变化和交付时更新 task 及最后修改时间。宣布交付前，按 task 模板写完整变更、验收证据、版本、前置输入、检查、未完成项与风险；记录缺失不构成完整交付，检查失败或验收未满足不得放行下游。

接收后、需仲裁时及交付时，在执行会话输出可复制摘要：任务 ID、编号、事实、记录位置及待处理事项，默认由用户转交主会话。文档写入不自动通知其他会话；其他通知渠道须已有授权。

执行状态全部由主会话更新，并记录转换时间与证据：

| 状态 | 进入条件 |
| --- | --- |
| unassigned | 尚无有效分配，或旧分配已撤销 |
| assigned | 有效分配和授权已登记，尚未读取接收记录 |
| running | 已读取有效接收记录，或交付被退回返工 |
| submitted | 已读取当前编号的完整交付记录，或已有交付需重新复核 |
| accepted | 当前有效交付经实际变更与检查审查接受 |

task 顶部 Draft / Accepted 只表示方案审查。阻塞原因另列，返工保留审查历史；不增加第二套执行状态。

主会话恢复协调时先读取最新回报并同步登记，再审查或派发。登记滞后不能导致重复分配或跳过交付审查。记录写入失败时，执行者说明“接收 / 交付记录未完成”及原因，提供待补内容，不能宣称已登记 submitted 或已被接受。

## Changes and reassignment / 变更与重新分配

执行中需要改变目标、范围、方案或依赖时，先暂停受影响实施并回报主会话，按阶段规则完善意图或计划。修订方案在完成并重新接受前保持 Draft；评估运行任务及下游版本，记录继续、暂停或重新分配的决定。

上游变化时暂停受影响任务的新派发。已接受的下游需要复核时回到 submitted，需返工时安排授权、基线和有效编号；不能沿用失效的 accepted 交付。

撤销前核实原执行者停止，或协调剩余共享修改；无法核实时保持阻塞，超时不代表停止。记录撤销原因、旧编号和结果位置，再安排新编号。旧编号迟到交付仅供主会话重新核对，不能自动替代当前结果。

竞争请求由主会话顺序处理。此单一写入者约定依赖参与者遵守，Markdown 不提供原子互斥或自由认领。

局部交付审查用于放行依赖；整体 Verification 负责对齐检查、修复与复验。验证修复涉及 task 时，主会话按现有分配规则明确修复执行者与写入范围，将需返工的交付置为 running；修复后更新 task 版本与检查证据，经 submitted 审查后再 accepted，并复核受影响的下游结果。此类修复沿用验证授权，既定方案继续有效。
